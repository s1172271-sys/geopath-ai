# GeoPath AI 题库数据结构设计方案

> 版本：v1.0  
> 适用范围：当前单文件 GeoPath AI 教学原型  
> 目标：让题目内容与程序逻辑分离，使扩题、校对、翻译、测试和后续接入 AI 更容易  
> 说明：本文只是设计方案，不修改现有网页代码。

---

## 一、为什么需要重新设计题库

目前每道题的内容分散在三个地方：

1. `questionBank`：题干、已知、求证、提示、参考证明、图形。
2. `socraticFlows`：苏格拉底问答步骤。
3. `reasoningFlows`：分步推理的答案和反馈。

这种写法对 4 道题还可以，但题目一多会出现问题：

- 同一道题的内容分散，修改时容易漏改。
- 中英文内容用 `_zh`、`_en` 后缀，字段越来越多。
- 每道题的图形、提示、评分规则混在程序里。
- 新增一道题要同时改很多地方。
- 没有统一格式，无法自动检查“是否漏了英文”“答案是否泄露”。
- 很难做多解法、动态几何任务和教师录题工具。

所以建议把题库设计成一套**统一格式的题目数据**，程序只负责读取和展示。

可以把它理解成：

> 题库是“教材”，程序是“教室”。  
> 以后换教材、加题目，不需要重盖教室。

---

## 二、设计原则

### 1. 一道题一个完整对象

每道题的所有内容放在一个题目对象里，不再分成三个互不关联的数据块。

### 2. 内容与程序分离

题目文字、提示、证明、评分规则、苏格拉底问题、图形命令都放在数据里。

程序只负责：

- 读取题目
- 显示题目
- 检查答案
- 操作图形
- 记录进度

### 3. 中英文使用同一种结构

不要再用 `title_zh`、`title_en` 这种成对字段，而是统一写成：

```json
{
  "zh": "中文内容",
  "en": "English content"
}
```

这样以后加第三种语言也容易。

### 4. 答案与题目放在一起，但结构清晰

每道题的答案、评分规则、常见错误都放在题目的 `reasoning` 部分。

### 5. 先支持一条主解法，再预留多解法

第一版可以只做一条标准证明路径，但数据结构要允许以后加入其他正确路径。

### 6. 所有题目都要能被自动测试

每道题都带一组测试用例，确保以后改程序不会把某道题改坏。

### 7. 图形与题目绑定

GeoGebra 构造、显示范围、测量项、静态 SVG 备用图，都属于这道题的数据。

### 8. 不给非程序员制造代码负担

录题时主要填写文字、选项、步骤和图形参数，不需要写复杂程序。

---

## 三、推荐的总体结构

建议把项目分成四层：

```text
GeoPath AI
├── 界面层：首页、答题页、弹窗
├── 程序层：渲染、检查、GeoGebra、进度
├── 题库层：每道题一份数据
└── 公共资源层：理由字典、知识点标签、图形文件、翻译
```

题库层建议长这样：

```text
data/
├── index.json                 题目索引：有哪些题、顺序、状态
├── reasons.json               推理理由字典
├── tags.json                  知识点和难度标签
├── questions/
│   ├── L1_Q1.json
│   ├── L2_Q1.json
│   ├── L3_Q1.json
│   └── L4_Q1.json
├── diagrams/
│   ├── L1_Q1.svg
│   ├── L1_Q1.aux.svg
│   └── ...
└── schemas/
    └── question.schema.json   题目格式规范
```

如果你希望继续“双击 HTML 就能打开”，可以再加一个构建步骤：

> 编辑时使用分开的 JSON 文件，发布时自动打包成一个内嵌题库的 HTML。

这样既能方便维护，又不需要每次都启动服务器。

## 四、题目对象的整体结构

每道题建议包含以下部分：

| 部分 | 作用 |
|---|---|
| `schemaVersion` | 数据格式版本 |
| `id` | 题目唯一编号 |
| `version` | 题目内容版本 |
| `status` | 草稿、审核中、已发布、已归档 |
| `metadata` | 难度、年级、知识点、题型、作者等 |
| `presentation` | 标题、题干、已知、求证、策略、误区、图形说明 |
| `hints` | 3 条递进提示 |
| `proof` | 参考证明步骤 |
| `reasoning` | 分步推理、目标、答案、理由、反馈、测试 |
| `socratic` | 苏格拉底问答链 |
| `geometry` | GeoGebra 构造、测量项、静态 SVG |
| `tests` | 自动测试用例 |
| `analytics` | 可选：技能标签、预计用时等 |

## 五、字段详解

### 5.1 基本信息

```json
{
  "schemaVersion": "1.0",
  "id": "L1_Q1",
  "version": 1,
  "status": "published"
}
```

| 字段 | 说明 |
|---|---|
| `schemaVersion` | 数据格式版本，例如 `1.0` |
| `id` | 永久唯一编号，建议不要重复使用 |
| `version` | 题目内容改动一次就加 1 |
| `status` | `draft`、`review`、`published`、`archived` |

题目编号建议保持稳定，例如：

- `L1_Q1`
- `L2_Q1`
- 以后可以扩展为 `G8_TRIANGLE_001`

不要用“第 1 题”这种会变化的编号。

---

### 5.2 元数据 `metadata`

```json
{
  "metadata": {
    "level": 1,
    "difficulty": 2,
    "grade": "八年级",
    "curriculum": ["初中几何", "全等三角形"],
    "knowledgePoints": ["线段加减", "平行线性质", "SAS 全等判定"],
    "questionType": "proof",
    "estimatedMinutes": 8,
    "source": "自编题",
    "author": "GeoPath AI 项目组",
    "reviewedBy": "数学教研审核",
    "createdAt": "2026-11-03",
    "updatedAt": "2026-11-03"
  }
}
```

| 字段 | 说明 |
|---|---|
| `level` | 关卡等级，决定首页卡片显示 L1～L4 |
| `difficulty` | 1～5，表示题目难度 |
| `grade` | 适用年级 |
| `curriculum` | 所属课程或单元 |
| `knowledgePoints` | 知识点标签，便于以后筛选和推荐 |
| `questionType` | `proof`、`calculation`、`construction`、`multiple_choice` |
| `estimatedMinutes` | 预计完成时间 |
| `source` | 题目来源 |
| `author` | 出题人 |
| `reviewedBy` | 审核人 |
| `createdAt` | 创建日期 |
| `updatedAt` | 最后修改日期 |

这些字段不一定马上全部用到，但以后做题库管理、筛选和统计时会很有用。

### 5.3 展示内容 `presentation`

```json
{
  "presentation": {
    "title": {
      "zh": "等级 1：基础几何关系认知",
      "en": "Level 1: Geometric Relationship Recognition"
    },
    "statement": {
      "zh": "如图，点 A、D、B、E 在同一直线上……",
      "en": "As shown, points A, D, B, E lie on the same straight line……"
    },
    "givens": {
      "zh": ["A、D、B、E 四点共线", "AD = BE", "AC // DF", "AC = DF"],
      "en": ["A, D, B, E are collinear", "AD = BE", "AC // DF", "AC = DF"]
    },
    "target": {
      "zh": "BC = EF",
      "en": "BC = EF"
    },
    "strategy": {
      "zh": "线段转换与 SAS 直接全等判定",
      "en": "Segment transformation and SAS direct congruence"
    },
    "commonMisconception": {
      "zh": "容易误以为无需证明 AB = DE。",
      "en": "Students may assume AB = DE without proving it."
    },
    "diagramAlt": {
      "zh": "A、D、B、E 共线，三角形 ABC 与 DEF 的一组对应边和角相等。",
      "en": "A, D, B, E are collinear; triangles ABC and DEF have corresponding equal parts."
    }
  }
}
```

说明：

- `givens` 是列表，方便页面逐条显示。
- `diagramAlt` 是图形说明，方便无障碍阅读，也可以作为学生看不到图时的文字补充。
- 题干和已知分开，避免页面显示时重复。

### 5.4 提示 `hints`

```json
{
  "hints": [
    {
      "id": "h1",
      "level": 1,
      "text": {
        "zh": "观察线段 AD 和 BE，它们都加上中间线段 DB 后，能组成哪两组新线段？",
        "en": "Observe AD and BE. What new segments form when adding DB to both?"
      }
    },
    {
      "id": "h2",
      "level": 2,
      "text": {
        "zh": "因为 AC // DF，根据平行线的性质，哪一对同位角相等？",
        "en": "Since AC // DF, which corresponding angles are equal?"
      }
    },
    {
      "id": "h3",
      "level": 3,
      "text": {
        "zh": "在 △ABC 和 △DEF 中，我们已有两组边及它们的夹角相等，可以使用什么判定定理？",
        "en": "In △ABC and △DEF, which congruence test applies to two sides and the included angle?"
      }
    }
  ]
}
```

建议：

- 每道题 3 条提示。
- 提示 1 只指方向。
- 提示 2 指向关键定理或关系。
- 提示 3 给出接近答案的突破点，但仍不直接写完整证明。
- `level` 决定显示顺序。

### 5.5 参考证明 `proof`

```json
{
  "proof": {
    "title": {
      "zh": "分步标准证明",
      "en": "Step-by-step Reference Proof"
    },
    "steps": [
      {
        "id": "p1",
        "statement": {
          "zh": "∵ AD = BE",
          "en": "Since AD = BE"
        },
        "reason": {
          "zh": "已知条件",
          "en": "Given"
        },
        "dependsOn": []
      },
      {
        "id": "p2",
        "statement": {
          "zh": "∴ AD + DB = BE + DB，即 AB = DE",
          "en": "AD + DB = BE + DB, so AB = DE"
        },
        "reason": {
          "zh": "等式性质",
          "en": "Property of Equality"
        },
        "dependsOn": ["p1"]
      }
    ]
  }
}
```

`dependsOn` 表示这一步依赖前面哪些步骤。

第一版可以只用来展示；以后做“证明结构图”或“形式化检查”时，它会很重要。

### 5.6 分步推理 `reasoning`

这是题库的核心部分，也是目前 `reasoningFlows` 的升级版。

```json
{
  "reasoning": {
    "defaultPathId": "main",
    "paths": [
      {
        "id": "main",
        "title": {
          "zh": "标准证明路径",
          "en": "Standard proof path"
        },
        "steps": [
          {
            "id": "s1",
            "order": 1,
            "task": {
              "zh": "先处理 AD = BE，把它变成与两个三角形边有关的关系。",
              "en": "Turn AD = BE into a relation involving sides of the two triangles."
            },
            "goals": [
              {
                "id": "seg-add",
                "text": {
                  "zh": "利用线段加法，把已知的相等线段转化成三角形的边",
                  "en": "Use segment addition to turn the given equal segments into triangle sides"
                }
              },
              {
                "id": "jump",
                "text": {
                  "zh": "直接写出最终结论，跳过中间关系",
                  "en": "Write the final conclusion directly and skip intermediate relations"
                }
              }
            ],
            "correctGoalId": "seg-add",
            "acceptedRelations": [
              {
                "type": "equality",
                "value": "AB = DE"
              }
            ],
            "acceptedReasons": ["equality"],
            "checks": {
              "relation": {
                "zh": "A、D、B 三点共线，AB 由 AD 和 DB 组成；两边同时加上 DB 会得到什么？",
                "en": "A, D, B are collinear. What happens when DB is added to both sides?"
              },
              "reason": {
                "zh": "这一步把 DB 加到等式两边。应该选择哪一个理由？",
                "en": "This step adds DB to both sides. Which reason describes that?"
              }
            },
            "feedback": {
              "correct": {
                "zh": "对。AD = BE，两边同时加上 DB，就得到 AB = DE。",
                "en": "Correct. Adding DB to both sides of AD = BE gives AB = DE."
              }
            },
            "misconceptions": [
              {
                "id": "skip-to-target",
                "match": {
                  "keywords": ["BC = EF", "直接证明"]
                },
                "response": {
                  "zh": "这是最终结论。先完成本步，把短线段转化成三角形的边。",
                  "en": "That is the final conclusion. First turn the short segments into triangle sides."
                }
              }
            ]
          }
        ]
      }
    ]
  }
}
```

关键字段说明：

| 字段 | 作用 |
|---|---|
| `defaultPathId` | 默认使用哪一条证明路径 |
| `paths` | 允许以后加入多条正确解法 |
| `steps` | 当前路径的步骤列表 |
| `task` | 本步任务说明 |
| `goals` | 下拉框中的推理目标选项 |
| `correctGoalId` | 正确目标，不在选项里直接写“correct” |
| `acceptedRelations` | 可接受的数学关系 |
| `acceptedReasons` | 可接受的理由 ID |
| `checks` | 写错时的检查问题 |
| `feedback` | 正确、部分正确、错误等反馈 |
| `misconceptions` | 常见错误及针对性回应 |

#### 为什么把 `correctGoalId` 单独放？

目前选项里带 `correct: true`，虽然前端数据本来就能被看到，但从数据设计上不够干净。

更好的方式是：

- `goals` 只放选项
- `correctGoalId` 单独记录答案

这样以后做“随机打乱选项”也更方便。

#### 反馈可以只写必要的

每个步骤至少写 `feedback.correct`。

其他四种反馈可以先不写，用全局模板：

- 部分正确
- 不正确
- 当前信息不足
- 数学表达不完整

如果某一步需要特别说明，再单独覆盖。

这样录题工作量不会太大。

#### `acceptedRelations` 的写法

建议存“标准写法”，不要把所有等价写法都列一遍，因为检查器本身会处理：

- 等号换边
- 系数比
- 角的顶点和端点顺序
- 平行关系换边
- 全等三角形对应映射

例如只写：

```json
{ "type": "equality", "value": "AB = DE" }
```

检查器应该能接受：

- `DE = AB`
- `AB=DE`
- `AB 等于 DE`

对于确实有多种正确关系的步骤，才列多条：

```json
"acceptedRelations": [
  { "type": "equality", "value": "AD = 1/2 AB" },
  { "type": "equality", "value": "2AD = AB" }
]
```

#### 多解法怎么预留？

第一版只做一条 `main` 路径。

以后若要支持多解法，可以增加：

```json
"paths": [
  { "id": "main", "title": {...}, "steps": [...] },
  { "id": "alternative-1", "title": {...}, "steps": [...] }
]
```

程序可以：

- 默认显示 `main`
- 允许学生选择“换一种方法”
- 在某个步骤分叉
- 完成后比较不同证明

第一版不必实现，但结构先留好。

### 5.7 苏格拉底问答 `socratic`

```json
{
  "socratic": {
    "intro": {
      "zh": "我们先不急着写完整证明。我会一次只问一个小问题。",
      "en": "We will not write the full proof yet. I will ask one small question at a time."
    },
    "complete": {
      "zh": "你已经完成了这道题的引导链。可以查看参考证明对照书写格式。",
      "en": "You completed the guided chain. Open the reference proof to compare the written format."
    },
    "steps": [
      {
        "id": "soc1",
        "label": {
          "zh": "第 1 步：识别已知条件",
          "en": "Step 1: Identify the givens"
        },
        "question": {
          "zh": "题目直接告诉了我们哪些相等或平行的关系？请至少说出两条。",
          "en": "Which equal or parallel relationships are stated directly? Name at least two."
        },
        "keyPoints": [
          {
            "id": "adbe",
            "label": {
              "zh": "AD = BE",
              "en": "AD = BE"
            },
            "match": {
              "keywords": ["AD = BE", "AD 等于 BE", "AD 和 BE 相等"],
              "regex": [
                { "source": "ad\\s*=\\s*be", "flags": "i" }
              ]
            },
            "ask": {
              "zh": "题目里哪两条线段被直接写成相等？",
              "en": "Which two segments are stated as equal?"
            }
          }
        ],
        "required": 2,
        "success": {
          "zh": "对。AD = BE、AC = DF、AC // DF 都是题目直接给出的条件。",
          "en": "Right. AD = BE, AC = DF and AC // DF are all stated directly."
        },
        "check": {
          "zh": "先只找题目文字里带“=”或“//”的句子。",
          "en": "First look only for sentences with = or //."
        },
        "simpler": {
          "zh": "你能找到题目中哪两条线段被写成相等吗？说出一组就可以。",
          "en": "Can you find one pair of segments stated as equal? One pair is enough."
        },
        "hints": [
          {
            "zh": "先找带“=”的句子，再找带“//”的句子。",
            "en": "First find sentences with =, then the one with //."
          }
        ],
        "misconceptions": [
          {
            "id": "confuse-given-target",
            "match": {
              "keywords": ["BC = EF"]
            },
            "response": {
              "zh": "BC = EF 是最终要证明的结论，不是题目直接给出的条件。",
              "en": "BC = EF is the target, not a given condition."
            }
          }
        ]
      }
    ]
  }
}
```

关键字段说明：

| 字段 | 作用 |
|---|---|
| `intro` | 对话开场白 |
| `complete` | 全部完成后的总结 |
| `steps` | 问题链 |
| `keyPoints` | 本步需要学生找到的关键点 |
| `required` | 至少找到几个关键点才算通过 |
| `success` | 通过后的解释 |
| `check` | 答错时的检查问题 |
| `simpler` | 点击“我暂时不知道”后的更小问题 |
| `hints` | 连续尝试失败后的提示阶梯 |
| `misconceptions` | 常见误区及回应 |

#### `match` 的两种写法

**关键词写法**（适合非程序员）：

```json
"match": {
  "keywords": ["AD = BE", "AD 等于 BE"]
}
```

**正则写法**（适合复杂表达）：

```json
"match": {
  "regex": [
    { "source": "ad\\s*=\\s*be", "flags": "i" }
  ]
}
```

建议：

- 能用关键词就用关键词。
- 只有表达变化很多时，才用正则。
- 关键词和正则可以同时存在，满足任意一个即可。

### 5.8 图形 `geometry`

```json
{
  "geometry": {
    "mode": "geogebra+svg",
    "geogebra": {
      "view": [-1, 9.5, -1, 5.5],
      "construction": [
        "A=(0,0)",
        "B=(5,0)",
        "D=Point(Segment(A,B))",
        "E=B+(D-A)",
        "C=(1.2,3.6)",
        "F=D+(C-A)",
        "sAB=Segment(A,B)",
        "sAC=Segment(A,C)",
        "sBC=Segment(B,C)",
        "sDF=Segment(D,F)",
        "sEF=Segment(E,F)"
      ],
      "objects": {
        "draggable": ["A", "B", "C", "D"],
        "derived": ["E", "F"],
        "segments": ["sAB", "sAC", "sDF"],
        "highlight": ["sBC", "sEF"],
        "aux": [],
        "hidden": []
      },
      "initialPositions": {
        "D": [2, 0]
      },
      "readouts": [
        { "type": "length", "a": "A", "b": "D", "label": { "zh": "AD", "en": "AD" } },
```

#### 关于 SVG 文件

第一版可以继续把 SVG 写在题目数据里，方便迁移。

```text

diagrams/L1_Q1.aux.svg
```

这样可以用 Illustrator、Inkscape 等工具画图，不需要改程序。

- 任务说明
- 判定条件
- 容差
- 成功反馈
- 失败反馈

## 九、数学关系的表示规范

### 9.1 统一使用“标准写法”

建议题目数据里统一写：

- 线段：`AB = DE`
- 角：`∠A = ∠FDE`
- 平行：`AC // DF`
- 全等：`△ABC ≅ △DEF`
- 不等式：`1 < AD < 4`

不要混用：

- `AB=DE` 和 `AB = DE` 都可以，但建议统一加空格，方便人阅读。
- 角不要一会儿写 `∠A`，一会儿写 `角A`。
- 全等不要一会儿 `≌`，一会儿 `≅`。

程序可以兼容，但数据统一后更容易校对。

### 9.2 检查器负责“等价”，数据只存“标准答案”

例如标准答案写 `AB = DE`，检查器应该自动接受：

- `DE = AB`
- `AB=DE`
- `AB 等于 DE`
- `AB 和 DE 相等`

不要把所有这些写法都列进数据。

### 9.3 多组正确关系才列多条

例如 L2 第 1 步可以接受：

```json
"acceptedRelations": [
  { "type": "equality", "value": "AD = 1/2 AB" },
  { "type": "equality", "value": "2AD = AB" }
]
```

如果检查器已经支持系数比，只写第一条通常也够。

### 9.4 数值范围

L3 的最终答案可以写：

```json
{
  "type": "range",
  "value": "1 < AD < 4"
}
```

以后如果要做“数值答案”，可以增加：

```json
{
  "type": "number",
  "value": 4,
  "tolerance": 0.01,
  "unit": "cm"
}
```

### 9.5 理由使用 ID

理由不要写中文全文，写 ID：

```json
"acceptedReasons": ["midpoint"]
```

中文和英文标签统一从 `reasons.json` 读取。

## 十、答案泄露与安全检查

需要明确一点：

> 只要答案数据放在前端，懂技术的人就一定可以看到。

所以这个结构适合：

- 课堂教学
- 练习
- 形成性评价
- 课程演示

不适合：

- 高利害考试
- 需要防止作弊的正式测评

如果以后要做正式考试，必须把评分放到后端：

```text
浏览器只发送学生答案
服务器保存标准答案并评分
浏览器只接收反馈
```

第一版仍然可以把答案放前端，但建议在页面中明确说明“这是教学练习原型”。

## 十二、如何从现有结构迁移

不要一次性重写。建议分五步。

### 第一步：冻结现有版本

先备份当前 HTML，确保随时可以退回。

### 第二步：定义格式

先确定：

- 题目对象有哪些字段
- 理由字典
- 图形数据格式
- 测试用例格式

### 第三步：只迁移 L1

把 L1 的：

- `questionBank` 内容
- `socraticFlows.L1_Q1`
- `reasoningFlows.L1_Q1`

合并成一份 `L1_Q1.json`。

然后做一个“适配器”，让旧程序能读取新格式。

### 第四步：对比测试

用 L1 做回归测试：

- 页面显示是否一致
- 提示是否一致
- 正确答案是否通过
- 错误答案反馈是否一致
- GeoGebra 是否正常
- 语言切换是否正常
- 学习进度是否正常

### 第五步：迁移其余题目

L1 验证通过后，再迁移 L2、L3、L4。

最后再删除旧的三个数据块。

### 旧字段对应关系

| 旧字段 | 新位置 |
|---|---|
| `title_zh` / `title_en` | `presentation.title.zh` / `.en` |
| `statement_zh` / `statement_en` | `presentation.statement` |
| `given_zh` / `given_en` | `presentation.givens` |
| `target_zh` / `target_en` | `presentation.target` |
| `hints_zh` / `hints_en` | `hints[].text` |
| `proofSteps` | `proof.steps` |
| `geoReadouts` | `geometry.geogebra.readouts` |
| `geo` 函数 | `geometry.geogebra.construction` + `objects` |
| `svg` 函数 | `geometry.svg` |
| `socraticFlows[id]` | `socratic` |
| `reasoningFlows[id]` | `reasoning` |
| `REASON_OPTIONS` | `reasons.json` |
| `REASON_KEYWORDS` | `reasons.json` 的 `keywords` |

## 十四、自动校验规则

建议写一个校验工具，录题后自动检查：

### 格式校验

- `id` 是否存在且唯一
- `schemaVersion` 是否支持
- 必填字段是否完整
- 中英文是否成对
- 数组是否为空
- 理由 ID 是否存在于 `reasons.json`

### 内容校验

- 每道题至少有 1 条提示
- 参考证明至少 1 步
- 推理路径至少 1 步
- 每一步至少有 2 个目标
- `correctGoalId` 必须存在于 `goals`
- `acceptedRelations` 不能为空
- `acceptedReasons` 不能为空
- 必须有 `feedback.correct`

### 泄露校验

检查以下位置是否直接出现当前步骤答案：

- 本步任务 `task`
- 目标选项 `goals`
- 提示 `hints`
- 检查问题 `checks`

答案是允许存在于 `acceptedRelations` 里的，但不能出现在学生作答前就能看到的文字中。

### 图形校验

- `objects` 中的对象名是否在 `construction` 里出现
- `readouts` 引用的点是否存在
- 可拖动点是否被错误固定
- 辅助对象是否默认隐藏
- SVG 文件是否存在

### 测试校验

- 每道题至少 5 个测试用例
- 正确用例必须返回 `correct`
- 错误用例不能返回 `correct`
- 测试失败时阻止发布

## 十六、关键设计决定汇总

如果只记住几件事，记住这些：

1. **一道题一个 JSON 文件**，不要再分散在三个数据块。
2. **所有文字统一用 `{ zh, en }`**，不要再用 `_zh` / `_en`。
3. **理由抽成公共字典**，题目只引用理由 ID。
4. **答案用标准写法存储**，等价写法交给检查器。
5. **每道题带测试用例**，防止改坏。
6. **图形数据也属于题目**，包括 GeoGebra 构造、测量项、SVG 备用图。
7. **先支持一条主路径，结构上预留多解法**。
8. **先迁移一道题验证，再批量迁移**。
9. **答案在前端可见，所以只适合教学练习，不适合正式考试**。
10. **题库和程序分离后，扩题才真正可控**。

## 十七、下一步建议

建议下一步先做两件事，不急着改现有网页：

1. **确定题目格式 v1.0**  
   从本文中删掉暂时不用的字段，留下最小可用版本。

2. **用 L1 做一份真实 JSON 样例**  
   把现有 L1 的内容完整迁移进去，作为后续题目的模板。

等这两件事确认后，再开始改程序。

这样可以避免“方案很漂亮，但迁移时发现字段不合适”的问题。
