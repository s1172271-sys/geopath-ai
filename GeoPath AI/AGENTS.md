# AGENTS.md — GeoPath AI 开发规则

> 本文件约束所有后续参与本项目的 AI 编程助手（包括但不限于 OpenCode、Copilot、Cursor、Claude、ChatGPT 等）。
> **本文件优先级高于助手的默认习惯。** 开始任何修改前，必须先完整阅读本文件。

---

## 0. 项目基本情况（先读这一段）

- **GeoPath AI 是一个已经存在、可以正常运行的网站**，不是需要从零开发的新项目。
- 当前主文件：`geopath_ai_geometry_proof_tutor.html`（单文件，HTML + CSS + JavaScript + 题库 + GeoGebra 配置全部在内）。
- 参考文件：
  - `geopath_ai_geometry_proof_tutor.backup.html`：旧版备份，**只读参考，禁止覆盖或删除**。
  - `题库数据结构设计方案.md`：题库外置方案。
  - `第一题内容填写模板.md`：给非程序员用的录题模板。
- 技术形态：纯前端、无后端、无数据库、无构建步骤，双击 HTML 或本地静态服务器即可运行。
- 版本管理：Git 仓库；`main` / `backup-v1` 保存初始可用版本，日常开发在 `feature-upgrade` 分支。
- 项目性质：**规则化教学原型**，不是真实 AI 大模型产品。界面文案不得夸大为“真实 AI”。

---

## 1. 核心原则（不可违反）

### 规则 1：这是已有项目，不是新项目
- 禁止把项目当作空白项目重新搭建。
- 禁止引入新的框架、构建工具或工程结构，除非用户明确要求并同意。
- 默认延续现有的单文件、纯前端、无后端结构。

### 规则 2：不允许随意重写整个项目
- 禁止整体重写 HTML、CSS 或 JavaScript。
- 禁止大规模格式化、重排、批量改缩进或替换整个文件。
- 禁止以“优化”“重构”为理由，未经用户同意改动大范围代码。

### 规则 3：不允许删除已存在且正常运行的功能
- 现有功能包括但不限于：四个等级关卡、分步推理工作区、苏格拉底引导、辅助线、三级提示、参考证明、GeoGebra 动态图、`?noggb=1` 静态图回退、中英切换、学习进度、重置功能。
- 即使用户要求“简化”，也必须先列出将被删除的功能并取得明确同意。
- 不得删除 `.backup.html` 等历史文件。

### 规则 4：每次只开发一个明确指定的功能
- 一次任务只处理一个功能点或一个明确的小修复。
- 禁止在一次修改中顺带做无关的“顺手优化”。
- 如果用户需求包含多个功能，先拆分为步骤，逐步确认后执行。

### 规则 5：修改代码之前，必须先阅读相关代码
- 先定位相关函数、数据结构、DOM 节点和 i18n 键，再动手。
- 至少阅读：
  - 目标功能所在代码段；
  - 与它共享状态或数据的函数；
  - 相关的题库 / 流程 / 翻译数据。
- 禁止在未阅读上下文的情况下直接改代码。

### 规则 6：尽可能采用局部修改
- 优先使用精确替换、局部插入，而不是整文件覆盖。
- 不无必要地改变文件结构、函数顺序、命名体系或缩进风格。
- 保持与周围代码一致的写法、命名和注释语言。
- 新增代码应放在语义最接近的位置，而不是随意堆到文件末尾。

### 规则 7：不允许随意修改现有题目内容、证明步骤和 GeoGebra 图形配置
- 未经明确授权，禁止改动：
  - `questionBank` 中的题干、已知、目标、提示、参考证明；
  - `socraticFlows` 中的引导问题、关键词、必需命中数；
  - `reasoningFlows` 中的步骤、目标、关系、理由和反馈文案；
  - `geo:` / `svg:` 图形构造、坐标、`geoView`、`geoReadouts`。
- 如果任务确实需要改题目内容，必须先说明改哪一题、改哪些字段、为什么改，并等待确认。
- 改写题目时必须保证：题目描述、图形、证明步骤、答案三者一致。

### 规则 8：修改后必须检查 JavaScript 错误、页面显示和相关功能
每次修改后至少完成以下检查：
- [ ] 浏览器控制台无新增报错（`console.error`、未捕获异常）。
- [ ] 首页能正常加载，进度卡片显示正确。
- [ ] 目标题目能正常打开。
- [ ] 相关按钮、输入框、下拉框可正常操作。
- [ ] 中英文切换后内容不丢失、不串行。
- [ ] 辅助线、提示、参考证明、重置功能未被破坏。
- [ ] GeoGebra 动态模式正常；`?noggb=1` 静态模式正常。
- [ ] 学习进度写入 / 显示正常。
- [ ] 刷新页面后状态符合预期。

本地测试命令（任选其一）：
```powershell

# 或启动本地服务器
python -m http.server 8765 --bind 127.0.0.1
# 打开 http://127.0.0.1:8765/geopath_ai_geometry_proof_tutor.html
```

### 规则 9：如果修改可能影响其他功能，必须先告诉用户
出现以下情况时，必须先说明影响范围并等待确认：
- 改动共享状态（如 `currentQIndex`、`socraticState`、`reasoningState`、`isAuxVisible`、`isMeasureVisible`）。
- 改动题库 / 流程 / i18n 的公共结构。
- 改动 `openQuestion`、`renderDiagram`、`resetQuestion`、语言切换等被多处调用的函数。
- 改动 `localStorage` 的键名或存储格式。
- 改动 GeoGebra 生命周期或全局失败标记。
- 任何可能导致旧数据、旧题目、旧进度失效的改动。

### 规则 10：不确定原有逻辑时，先提问，不要自行猜测
- 不确定某个变量含义、某个分支用途、某段代码是否还有用时，先询问用户或先做只读分析。
- 禁止凭猜测删除“看起来没用”的代码。
- 禁止凭猜测修改题目答案、几何关系或判定规则。
- 无法确认时，保留原逻辑，并在报告中标注疑问。

### 规则 11：不允许将 API Key 或密码直接写入前端代码
- 禁止把 API Key、Token、密码、私钥、数据库连接串写入 HTML、JS、CSS 或任何会被提交的文件。
- 前端代码天然对用户可见，任何密钥都不得放在前端。
- 如未来需要调用真实 AI 服务，必须通过后端代理，并使用 `.env` 保存密钥。
- `.env`、`*.key`、`*.pem`、`credentials.json` 等必须保持在 `.gitignore` 中。
- 发现代码中已有密钥时，立即停止并向用户报告，不要继续提交。

### 规则 12：每次完成任务后必须提交报告
报告至少包含以下四项：

1. **修改的文件**：完整路径 + 每个文件改了什么。
2. **主要修改内容**：按功能点说明，避免只写“优化了代码”。
3. **测试结果**：执行了哪些检查、结果如何、是否发现报错。
4. **已知问题 / 风险**：未完成项、副作用、需要用户确认的事项。

推荐报告模板：

```markdown
## 本次修改报告

### 1. 修改的文件
- `xxx.html`：...

### 2. 主要修改内容
- ...

### 3. 测试结果
- [x] 控制台无报错
- [x] 首页正常
- [x] 目标功能正常
- [x] 中英文切换正常
- [x] GeoGebra / 静态图正常
- [x] 学习进度正常

### 4. 已知问题 / 风险
- ...
```

## 2. 工作流程（每次任务按顺序执行）

1. **确认任务**：明确本次只做哪一个功能，写出验收标准。
2. **只读分析**：阅读相关代码，定位数据和 DOM，列出影响范围。
3. **风险说明**：如果可能影响其他功能，先告诉用户并等待确认。
4. **局部修改**：小步修改，保留原结构，不顺手重构。
5. **自测**：按规则 8 的清单逐项检查。
6. **提交报告**：按规则 12 输出四项内容。
7. **等待下一步**：不要擅自开始下一个功能。

- ❌ 删除或覆盖 `.backup.html`。
- ❌ 删除现有题目、流程、翻译键或功能入口。
- ❌ 未经确认修改题目内容、证明步骤、GeoGebra 配置。
- ❌ 把 API Key、密码、Token 写入前端或提交到 Git。
- ❌ 为“整理代码”而大范围改格式、改命名、改目录。
- ❌ 在未阅读代码的情况下直接修改。
- ❌ 一次提交多个无关功能。
- ❌ 把规则化原型宣传为真实 AI 产品。
- ❌ 未测试就报告“已完成”。

## 4. 建议的修改边界

- **允许直接做**：修文案错别字、修明确的 bug、补测试、补注释、更新文档、调整局部样式。
- **需要先说明**：改动共享函数、状态结构、题库字段、进度存储、GeoGebra 生命周期。
- **必须取得明确同意**：改题目内容、改证明逻辑、删功能、换技术栈、引入后端、引入新依赖。
